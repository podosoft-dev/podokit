Make the `podo update` preview say what `--apply` will do with a managed file you edited. It labelled every such file `conflict … you edited this; update would need a merge`, while `--apply` then reported 0 conflicts, because a file whose template did not change merges back to your version. The plan now shows `keep` for an edited file whose template did not change, and for one the new version no longer generates, and `merge` for an edited file whose template changed too. `--apply` keeps the `keep` files without a merge, so an update that changes none of your edited files no longer needs the previous version's templates from npm, and reports them as kept (the `skipped` count is now `kept`). With `--from <previous templates>`, the preview also runs each merge in memory and shows one that would leave conflict markers as `conflict`, so its counts match what `--apply --from` reports. A file that was owned and is managed from this version on is now compared with the template it came from, so edits made before the last lock refresh are kept or merged instead of overwritten. In a fresh clone or git worktree without `node_modules`, a project with an external module package (such as `@podosoft/podokit-module-blog`) no longer stops `podo update`, `podo diff <path>`, `podo restore`, and `podo remove` with `Cannot resolve module "blog" while updating the project.`; the message names the package and asks you to run `bun install` first.
