Stop the generated API and web server promptly while event streams or WebSockets are open. On `SIGTERM` the API stopped accepting connections and then waited for every open connection, so one open server-sent event stream or WebSocket kept it running until the orchestrator killed it (10 seconds under Compose, 40 on Kubernetes), and the built web server waited its whole `SHUTDOWN_TIMEOUT` for streams its `/api` proxy relayed. Both now stop accepting connections, end server-sent event streams at once so `EventSource` clients reconnect to another instance, give in-flight requests up to `SHUTDOWN_TIMEOUT` seconds (30 unless set, now read by the API too and validated at startup), force-close what remains, and exit; a second signal exits at once. The API also closes its services within 3 seconds, answers `503` `SHUTTING_DOWN` on `GET /health/ready` while it stops, and offers a `SHUTDOWN` service (`shutdown` in the plugin context) whose `onShutdown(listener)` lets application WebSocket routes close their sockets with `GOING_AWAY` (1001); the `sse` module's streams use it. Apps with WebSocket routes of their own should register each socket, or it keeps the API running until `SHUTDOWN_TIMEOUT` and is then cut.
