# Updating a generated project

PodoKit v1 updates Bun/Elysia v1 projects. It does not convert PodoKit 0.x
Node/NestJS projects in place.

## Project metadata

Every generated project commits:

- `.podokit/manifest.json` — PodoKit version, template, Bun toolchain, modules,
  and rendering answers.
- `.podokit/files.lock` — ownership tier and generated hash for every tracked
  file. Local environment files such as `.env` and `.env.docker` are never
  recorded; the committed `.env.example` and `.env.docker.example` are.

| Tier | Meaning | Example |
|---|---|---|
| managed | PodoKit owns the file and updates it safely | `apps/api/src/main.ts` |
| assembled | PodoKit rebuilds fenced registrations from the module set | `apps/api/src/app.ts`, `auth/auth.ts` |
| owned | Application code; PodoKit never overwrites it | routes, UI primitives, `app.extensions.ts` |

Agent guidance under `.claude/`, `.agents/`, and `.cursor/` is owned, except
PodoKit's own `podokit-*` skills in `.claude/skills/` and `.agents/skills/`,
which stay managed so their commands and APIs follow the installed version. An
update from a version that still recorded them as owned updates the unedited
ones and merges or reports the edited ones like any managed file. To keep your
own version of one, add its path to `ownedGlobs` in `.podokit/manifest.json` or
run `podo eject <path>`; a skill under another name is never touched.

## Inspect before updating

```bash
podo status
podo diff
podo doctor
podo update
```

Runtime providers have their own dry-run-first command and remain part of the
same managed manifest and lockfile:

```bash
podo provider list
podo provider set object-storage local
podo provider set object-storage local --apply
```

The apply step updates code and configuration and may add an implementation
module. It does not migrate or delete database rows, cache entries, queued jobs,
or stored objects. Follow the backup and data-migration boundary in
[Runtime providers](providers.md).

`podo diff` lists managed files whose content no longer matches what PodoKit
wrote. Give it paths to see what changed:

```bash
podo diff apps/api/src/main.ts tests/ui/smoke.ui.spec.ts
```

For each path it prints a unified diff from the template's version to the
working file, or says that the file matches, is missing, or is not generated by
PodoKit. It works for owned files too, so you can see what the template's
version of a route or an ejected file looks like now. The template is the one
the installed CLI ships; when that is newer than the project, the output says
so and the diff includes the upstream changes.

`podo update` is read-only. It rebuilds the current v1 template and modules in
memory and prints a per-file plan. `podo doctor` checks declared Elysia, Svelte,
and Better Auth versions against the supported ranges.

Apply only after reviewing the plan:

```bash
podo update --apply
```

During apply:

- unchanged managed files are replaced with the new generated version;
- assembled fenced regions are recomputed from the module graph;
- edited managed files use a 3-way merge when a previous template tree is
  available;
- conflicts are written with standard conflict markers and reported;
- owned files are never modified; and
- the manifest and lockfile advance only with the applied tree.

### Owned files whose template changed

PodoKit never writes an owned file after it seeds it, so an improvement to its
template, such as a corrected `.mcp.json` or a newer `.devcontainer`, does not
reach your copy by itself. The lock records which template content each owned
file came from, and `podo update` lists every owned file whose template changed
since then as `review`:

```text
  review    .mcp.json  (owned; the template changed, see podo diff .mcp.json)
```

`podo diff <path>` shows your file against the new template. Pass the previous
version's templates with `--from` to see what changed upstream instead:

```bash
podo update --from ./previous-podokit/templates
```

Copy what you want by hand. `--apply` leaves these files as they are, lists them
again, and records the new template, so the next update reports only later
changes. A file you ejected is reported the same way. Locks written before this
record existed cannot tell an edit from a template change; the plan counts the
owned files that differ from the new templates, and applying the update starts
the record.

The target module graph is authoritative. If a module gains a requirement,
PodoKit applies the dependency first so services, imports, package dependencies,
environment examples, and tests arrive together. A new provider capability
requirement, such as `sse` requiring `events`, adds the module that implements
the project's selected provider (`podo provider list`). The plan lists these
under "Modules to add".

A module that starts declaring a [direct API path](modules.md#module-direct-api-paths)
in a newer version gets it added to `.podokit/dev.json` and every deployment
profile. The plan lists these under "Direct API paths to add", including any it
cannot add and why, and `--apply` writes them. `.podokit/manifest.json` records
each module's applied paths, so a path you removed afterwards is not restored.

Modules configure in manifest order, so a provider always comes before the
modules that use it. `podo add` places a newly added provider ahead of installed
modules that require it, and `podo update --apply` moves a provider recorded
after its dependents back in front of them.

## Bun-only v1 boundary

PodoKit v1 manifests declare Bun 1.4.0. The removed `podo runtime set` command
is not a migration mechanism. A PodoKit 0.x manifest is rejected with a message
to use the final 0.x CLI:

```bash
npx @podosoft/podokit@0.17.4 status
npx @podosoft/podokit@0.17.4 update
```

This boundary is deliberate. Automatic conversion cannot safely infer custom
NestJS decorators, guards, interceptors, TypeORM repositories, middleware,
dynamic modules, or application-specific API semantics. Create a new v1 app
and migrate domain behavior with explicit endpoint and data-contract tests.

## External package modules

Upgrade an external module with Bun, then preview and apply its managed changes:

```bash
bun update @podosoft/podokit-module-blog
podo update
podo update --apply
```

The manifest records the package name and installed version. If the package is
missing from `node_modules`, update fails instead of silently removing its
files. When a 3-way merge requires a previous external module, registry access
to that recorded version is required.

## Module path migrations

Module manifests can declare atomic path migrations. PodoKit expands directory
moves in the preview, preserves edited bytes, applies exact text replacements,
updates lock paths and ownership globs, and records the migration identifier
only after success.

The preflight refuses to proceed if a destination exists, a replacement count
does not match, or an installed external package still ships an incompatible
layout.

## Removing a module

```bash
podo remove <module>
```

Removal reverses registrations, files, package overlays, environment
examples, and the direct API paths only that module declared. It refuses to remove a module required by another installed module,
keeps locally edited files, and never drops database tables.

## Taking ownership

```bash
podo eject apps/api/src/example.ts
```

Eject changes that exact path to the owned tier. Future updates neither restore
nor overwrite it, even when it is moved or deleted. Use this only when the
application accepts responsibility for keeping the file compatible.

To undo an eject, or to throw away local edits to a managed file:

```bash
podo restore apps/api/src/example.ts
```

Restore rewrites each path with the template's content and records that content
as the clean baseline in `.podokit/files.lock`, so the next update treats the
file as unedited. An ejected path also leaves the manifest's owned paths and is
managed again. Restore refuses files that the template or a module declares
owned, such as routes and UI primitives, and files PodoKit does not generate;
it writes nothing unless every path can be restored. It also refuses when the
project is on another PodoKit version than the CLI, because it would mix two
template versions: run `podo update --apply` first.

Modules can declare owned presentation paths and managed exceptions. This lets
public SvelteKit pages remain fully customizable while route loaders, reusable
logic, or agent workflows continue to receive safe updates.

## Extending the Elysia application

`apps/api/src/app.extensions.ts` is application-owned. Register custom services
or module descriptors there without editing assembled fences:

```ts
import type { PodokitModule, ServiceRegistry } from "./core/services";

export function configureServices(services: ServiceRegistry): void {
  // Register or override an application-owned service before startup freezes.
  void services;
}

export const extensionModules: PodokitModule[] = [];
```

For a new route, create an Elysia plugin, validate inputs with `t`, throw
`AppException` with a stable code, declare OpenAPI details, register its access
policy, and add Bun tests plus an API contract entry. An `AppException`'s
optional fourth argument reaches the client as `error.details`, for example
`new AppException("SIGNUP_INVALID", "Invalid sign-up", 422, { fields })`.

### API extension files

Each of these application-owned files starts empty, is imported by a managed
file, and is created once by `podo update` in an existing app and never
overwritten afterwards. Use them instead of editing the managed file.

| File | Export | Use it instead of editing |
| --- | --- | --- |
| `apps/api/src/database/entities.ts` | `APP_ENTITIES` (TypeORM entity classes) | `database/data-source.ts`: the migration data source loads them, so `migration:generate` compares them with the database |
| `apps/api/src/core/api-contract.extensions.ts` | `APP_DOCUMENTED_ROUTES` (`"GET /reports/{id}"` or `"GET /reports/:id"`) | `scripts/verify-api-contract.ts` and `core/api-contract.ts`: `bun run contract` fails when one is not registered or not in the OpenAPI document |
| `apps/api/src/settings/app-flags.ts` (auth module) | `APP_FLAG_DEFAULTS` (`{ reportsEnabled: true }`) | `settings/flag-defaults.ts`, `auth/auth.module.ts`, and a migration seeding a row: the flags are stored with PodoKit's, set with `PUT /account/settings`, read with `SettingsService.getBool()`, and returned as `appFlags` by `GET /account/capabilities` |
| `apps/api/src/worker.extensions.ts` (bullmq module) | `configureWorkers(setup)` returning `{ queue, processor, options? }[]` | `jobs/worker.module.ts` and `main-worker.ts`: the worker process consumes these queues and runs `setup.onClose` after its workers stop |
| `apps/api/scripts/build.extensions.mjs` | `appBuildTargets` (`{ entrypoint, outdir }[]`) | `scripts/build.mjs`: the API build bundles these entry points too, and fails when one does not exist |
| `apps/api/src/config/env.extensions.ts` | `appEnvShape` (zod fields) and `refineAppEnv(env, context)` | `config/env.validation.ts`: application variables are validated at startup and typed on `AppEnv`; redefining a PodoKit variable fails |

## Extending the web app

The web app's framework files are managed. Application changes go in the owned
files listed under [web extension points](templates.md#web-extension-points):
Vite and SvelteKit options in `apps/web/vite.extensions.ts`, styles in
`apps/web/src/app.extensions.css`, and with
`admin-dashboard` a request hook in `apps/web/src/lib/server/app-hooks.ts`,
admin sidebar entries in `apps/web/src/lib/admin/app-nav.ts`, Settings switches
for the API's application flags in `apps/web/src/lib/admin/app-flags.ts`, and private page
prefixes in `apps/web/src/lib/server/non-indexable-paths.ts`. `podo update`
creates each of them once in an existing app. An app that edited the managed
`vite.config.ts`, `app.css`, `hooks.server.ts`, `admin-sidebar.svelte`, or
`search-indexing.ts` gets a merge or a conflict there; move the edit into the
owned file and take PodoKit's version of the managed one.

### Extending the web proxy

The SvelteKit `/api` proxy, `apps/web/src/lib/server/backend-proxy.ts`, is
managed. Instead of adding header names to its lists, put them in the
application-owned `apps/web/src/lib/server/proxy-headers.ts`
(`APP_FORWARDED_REQUEST_HEADERS` and `APP_RELAYED_RESPONSE_HEADERS`); see
[proxy headers](templates.md#proxy-headers). Per-route request body limits go in
the owned `apps/web/src/lib/server/body-limits.ts` (`APP_BODY_LIMITS`); see
[request body limits](templates.md#request-body-limits), and per-route response
deadlines, including routes without one, in the owned
`apps/web/src/lib/server/proxy-timeouts.ts` (`APP_PROXY_TIMEOUTS`); see
[proxy deadlines per route](templates.md#proxy-deadlines-per-route). An app that already added names to
the managed lists keeps them through `podo update`, because the new version adds
its merge below the lists; move the names to the owned file and restore the
managed copy so the next update is clean.

## Compatibility ranges

| Framework | Supported range |
|---|---|
| `elysia` | `^1.4` |
| `svelte` | `^5` |
| `better-auth` | `>=1.7.1 <1.8` |

`podo doctor` warns when an application moves outside these ranges.

Better Auth 1.7.3 restored account identity to `(providerId, accountId)` and
removed the required `issuer` introduced in 1.7.0–1.7.2. Back up populated
databases before upgrading. The generated `migrate:all` command checks for
duplicate identities before changing constraints and stops for manual resolution
if it finds collisions. It preserves account rows, user links, and passwords.

For PostgreSQL, it makes a legacy `issuer` column nullable, preserves its values,
and removes the obsolete issuer index and PodoKit compatibility trigger. For
SQLite, it drops the obsolete index and unused column. Both paths enforce unique
`(providerId, accountId)` identities, support repeated runs, and leave fresh or
1.6 schemas without an `issuer` column. Custom indexes or constraints may require
manual cleanup. Microsoft accounts may still need a trusted `sub`-to-`oid` mapping;
follow the [official upgrade guide](https://github.com/better-auth/better-auth/blob/main/docs/content/docs/guides/1-7-upgrade-guide.mdx)
for those accounts rather than guessing an identity.

### Better Auth 1.7.7 security update

New authentication modules and the API client require at least 1.7.7 for Better
Auth and their matching integrations. Existing applications should upgrade the
server, API key, passkey, and OAuth provider packages together and regenerate
their dependency lockfile.

When API instances share verification storage, upgrade them in the same
cutover. Request new Magic Links and restart OAuth or cookie-backed SAML sign-ins
that began before the upgrade. OAuth Proxy participants must also upgrade
together. Upgrading from 1.7.6 to 1.7.7 requires no schema change. Databases with
the older 1.7.0–1.7.2 issuer constraints need the cleanup described above before
authentication starts.

Custom `verification.storeIdentifier.overrides` rules must account for the
`magic-link:` and `auth-state:` prefixes. Existing endpoints and token formats
remain the same. See the [official 1.7.7 release notes](https://github.com/better-auth/better-auth/releases/tag/v1.7.7)
and [Magic Link security advisory](https://github.com/better-auth/better-auth/security/advisories/GHSA-965c-763c-88jm).
